# RuyiTrace 整体进度评估（2026-11-20）

> 编译只是验证手段。本文回答：**RuyiTrace 这个项目实际完成了多少。**

---

## 当前验收（Linux core writer）

上一版实验内核已链接 libxul 并进入 headless，采集目录为空；其 networking 构建审计曾被跳过，不作为发布构建。后续接入尝试缺父级 DIRS，导致链接找不到运行时符号。现在已有 Linux 父构建补丁及本机验证的 core 写入路径：20 项宿主测试通过，其中新增并发落盘和限流测试。没有进行新一轮远程构建。

独立测试使用**合成事件**，不是从页面采集。下一里程碑是让真实绑定向 `Finish` 提交正确名称与值，取得同一次本地页面运行里的 `Document.title` set/get 和 `Document.createElement` call，并验证关闭时零输出。此前的格式分析、主机测试及启动验证均不能替代该验收。

## 此前阶段快照（以下非当前构建状态）

**分析层与实现层基本完成，运行验证层完全没开始。**

### 做扎实的部分

| 项 | 为什么可信 |

| 项 | 推断程度 |

代码能编译，逻辑自洽，测试通过——但**没有一次真实采集**。

## 五、下一步真正的瓶颈

不是代码，是**一台 32 GB 内存的机器**。

| 需求 | 现状 | 差距 |
| --- | --- | --- |
| 内存 | 15 GB（host185） | 需 32 GB |
| 已有产物 | 18 GB 源码 + objdir | 可复用 |
| `gkrust` 编译 | 已尝试 3 次，全部 OOM | 关 LTO 后仍需 12 GB+ |

**有了 32 GB 机器，剩下的路是清楚的**：

1. `docker update --memory=28g`
2. `mach build` → 得 `libxul.so`
3. 跑 `MOZ_DOM_TRACE=1` 采一次
4. 对比 win64 版的输出格式
5. 联调控制台

预计 4–6 小时。
